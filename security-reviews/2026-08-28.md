# Security review: pre-vendor diligence (upstream baseline)

**Review date:** 2026-08-28
**Reviewed commit:** `8a024df` (upstream `taiidani/terraform-provider-jenkins` `main`, before any Kensho changes)
**Reviewed by:** Dogacan Colak, with Claude Code
**Scope:** the whole upstream provider as vendored. Kensho's own additions (the four `*vault_*` resources/data sources) were explicitly out of scope for this pass.
**Context:** Kensho is vendoring this third-party provider in to manage Jenkins credentials as code and use Vault as the single source of truth for secrets. The provider holds Jenkins **admin** credentials and talks to `jenkins.infra.kensho.com`. Prompted by Dave's caution: "be very careful about using a 3rd party tf provider for jenkins."
**Method:** read-only audit across three slices (credential/secret handling; transport, injection, XML and egress; build/release supply chain). The load-bearing transport findings were verified against the pinned gojenkins source in the module cache, not inferred.

## Verdict

**Reasonable to vendor, with fixes.** No HIGH findings; no code-execution, injection, XXE or egress issues. The credential-handling layer is clean by design. There are two transport weaknesses worth fixing before this holds admin credentials in production, plus two process obligations Kensho must own for the private-registry republish. All are addressable in our fork.

Both MEDIUM findings (M1, M2) are in **upstream** code, not in Kensho's additions. As of this review they are **recorded and deferred**, not remediated.

## Findings

### MEDIUM (upstream; deferred as of this review)

**M1: `ca_cert` provider option is a silent no-op in the pinned client.**
`jenkins/config.go:34-38` assigns the CA bytes to `client.Requester.CACert`, but the pinned `bndr/gojenkins v1.1.1-0.20210407143218-9e2483ff7ebd` **never reads** `CACert` or `SslVerify`. Verified: those fields are only declared (`request.go:61-62`), set in the constructor (`jenkins.go:605`), and mentioned in the README; there is no `tls.Config`, `TLSClientConfig`, `CertPool` or `AppendCertsFromPEM` anywhere in the library. Because the provider calls `CreateJenkins(nil, ...)`, the client falls back to `http.DefaultClient` (`jenkins.go:604-607`).

Net effect: TLS uses the **system trust pool with full verification** (verification is *not* disabled), but a supplied `ca_cert` does nothing. Practical impact: (a) false assurance that trust is pinned to an internal CA; (b) an internal-CA-only Jenkins cert fails to connect rather than silently downgrading, which can tempt an insecure workaround. The read error is also swallowed (`_`).

*Fix:* in `config.go`, build an explicit `*http.Client` with `tls.Config{RootCAs: pool}` where `pool` is a clone of `x509.SystemCertPool()` plus the supplied CA (augment, never replace), and pass it into `CreateJenkins(client, ...)`. Surface the read and append errors instead of discarding them. Add an integration test against a Jenkins presenting an internal-CA-only cert.

**M2: plain `http://` `server_url` is permitted (no scheme enforcement).**
`server_url` (`jenkins/provider.go` schema, mirrored in `provider_framework.go`) is a free-form string; nothing rejects `http://`. gojenkins sends Basic-Auth admin credentials on **every** request (`request.go`, `SetBasicAuth`). A cleartext URL (a typo, or a `JENKINS_URL` env default) leaks the admin password to any on-path observer.

*Fix:* validate that `server_url` uses `https://`, allowing `http` only for explicit localhost test targets, and fail fast in Configure otherwise. For the Kensho fork, enforce HTTPS unconditionally.

### Process obligations (own before publishing to the private registry)

**P1: re-establish the trust chain for the private registry.**
Upstream release hygiene is good: goreleaser emits sha256 checksums and GPG-detach-signs the checksum file, release CI SHA-pins goreleaser and import-gpg, and secrets are confined to a tag-triggered job that never checks out untrusted PR code. But that signature is taiidani's, and it carries no meaning once Kensho republishes to its own registry. Kensho must pin an immutable upstream tag, verify `*_SHA256SUMS` and its `.sig` against taiidani's known public key, verify each zip, and only then re-sign with a Kensho-controlled key registered in the private registry. Building from source at the audited commit is preferable to repackaging upstream binaries. Nothing in the repo enforces any of this.

**P2: `bndr/gojenkins` is the one real provenance wart.**
Single-maintainer personal module, pinned to an untagged 2021 commit (`v1.1.1-0.20210407143218-9e2483ff7ebd`), sitting **directly on the Jenkins-admin-credential path**. It is not a typosquat, and `go.sum` pins it immutably so there is no live-swap risk, but dependabot will not meaningfully update a commit-pin. Mirror it through Kensho's GOPROXY and track it for CVEs manually. Note also that any fix for M1 which relies on the library honoring `ca_cert` would first need a version that actually wires TLS, which is why M1's recommended fix builds our own `http.Client` instead.

### LOW and informational

- **L1:** AWS `access_key` is marked `Sensitive: true` (`resource_jenkins_credential_aws.go:70`, data source `:47`). Over-classification of a public key ID; harmless, no leak.
- **L2:** the pinned gojenkins has a `log.Printf("DEBUG ...")` **response**-dump path (`request.go:233-238`) gated on `ctx.Value("debug")`. Dead code here, since the provider never sets a `"debug"` context key. It becomes a landmine only if Kensho later adds request tracing using that key name.
- **N1 (non-security, upstream functional bug):** `resource_jenkins_credential_azure_service_principal.go:302-304`: `Update` assigns `certificate_id` into `cred.Data.ClientId` instead of `CertificateId`. Worth upstreaming a fix; not a secret leak.

## Areas audited and confirmed clean

- **Secrets in logs and state:** no secrets reach logs, tflog, prints or error strings. Every `Read()` deliberately does *not* read secrets back into state (the consistent "GetSingle returns garbage" pattern). All secret schema attributes are correctly `Sensitive: true`. Data sources omit secret attributes entirely. The admin password flows only into Basic-Auth and is never logged. No hardcoded credentials ship in the binary.
- **Injection and RCE:** no `os/exec` and no shelling out anywhere; the command-injection surface is nil.
- **XXE:** XML is parsed only via Go stdlib `encoding/xml` (`folder.go:42`), which does not resolve external entities. No custom decoder, `CharsetReader`, entity map, or third-party XML parser.
- **SSRF:** user-controlled names, folders and ids are validated (they reject `/`) and only ever land in URL **path** positions under an already-fixed host and scheme, so they cannot control host or protocol.
- **Egress:** no telemetry, update check, or phone-home. All traffic goes to the configured `server_url`.
- **Dependency tree (besides gojenkins):** HashiCorp-official and stdlib-adjacent modules, full `go.sum` hashes, doc-generation deps isolated in `tools/go.mod` so they never enter the released binary.
- **CI:** no `pull_request_target` misuse, no `github.event.*` interpolation into `run:` steps, no build-time remote code fetch or execution.
